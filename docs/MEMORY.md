## MEM-001 - Two separate git repositories

**Status:** Verified
**Source:** `AGENTS.md` section 2 ("TWO SEPARATE GIT REPOS - HARD RULE"); `docs/RULES.md` RULE-CI-001; `.gitignore` line ~43 (excludes `nrega-server/`); git config of each repo.

**What we know:** NREGA Bot is split across two independent git repositories:

| Repo | Folder | Remote | Branch |
|---|---|---|---|
| Desktop app | `.` (root) | `https://github.com/rajatpoddar/NregaBot.git` | `main` |
| Server (Flask) | `nrega-server/` | `ssh://rajat@192.168.29.101:/volume1/docker/nrega-server.git` (NAS) | `master` |

`nrega-server/` has its own `.git`; desktop repo's `.gitignore` ignores it (line ~43). They are NOT submodules - nested repo with own history.

**Why it matters:** Mixing commits or pushing to the wrong remote can break production deploys. Each repo deploys independently.

**Related files:** `.gitignore`, `nrega-server/.git`, `docs/RULES.md` RULE-CI-001.
**Related phase/commit:** Permanent (project structure).

## MEM-002 - Codebase Memory workflow

**Status:** Verified
**Source:** `AGENTS.md` section 5 ("Codebase Memory workflow"); `docs/RULES.md` RULE-CM-001; tools `codebase-memory-mcp__*`.

**What we know:** The project uses codebase-memory-mcp to maintain a knowledge graph of the codebase. ALWAYS prefer MCP graph tools over grep/glob/file-search for code discovery.

Priority order:
1. `search_graph` - find functions, classes, routes, variables by pattern.
2. `trace_path` - trace who calls a function or what it calls.
3. `get_code_snippet` - read specific function/class source code.
4. `check_index_coverage` - validate candidate paths and missed ranges.
5. `query_graph` - run Cypher queries for complex patterns.
6. `get_architecture` - high-level project summary.

**Why it matters:** The graph has 2,509 nodes / 15,228 edges (per audit 29 Aug 2026). Grep-based search misses implicit contracts (e.g., the `host class` comment at `app_automation.py:143-153`).

**Related files:** MCP graph DB (`.codebase-memory/`).
**Related phase/commit:** Permanent (MCP infrastructure).

## MEM-003 - Locale generation pipeline (CI-controlled)

**Status:** Verified
**Source:** `AGENTS.md` section 3.7 ("Generated locale JSON is CI-controlled"); `docs/RULES.md` RULE-LOC-001 and RULE-LOC-002; `scripts/build_locales.py`; `scripts/translations_{kn,bn,hing}_{1..5}.py`.

**What we know:**

- `src/locales/kn.json`, `bn.json`, `hinglish.json` are **build artifacts**, generated by `scripts/build_locales.py` from `scripts/translations_{kn,bn,hing}_{1..5}.py`.
- `src/locales/en.json` and `hi.json` are manually edited.
- CI runs `build_locales.py` and **exits non-zero** on missing/unused/placeholder-mismatch keys (release blocker).

Adding a new key:
1. Add to `en.json` AND `hi.json`.
2. Add to `translations_kn_5.py`, `translations_bn_5.py`, `translations_hing_5.py` (last part files).
3. Run `build_locales.py` - exit 0.
4. `{placeholder}` tokens identical across languages.

**Why it matters:** The 3.2.3 release failed CI due to 6 missing keys. The protocol prevents that class of bug.

**Related files:** `scripts/build_locales.py`, `scripts/translations_*.py`, `src/locales/{en,hi,kn,bn,hinglish}.json`.
**Related phase/commit:** Permanent.

## MEM-004 - Release hash workflow

**Status:** Verified
**Source:** `AGENTS.md` section 3.2 ("Agent NEVER fills release hashes"); `docs/RULES.md` RULE-REL-002; `config/version.json`.

**What we know:**

- The agent MUST NEVER fill hashes (`hash`, `hash_windows`, `hash_macos`) in `config/version.json`.
- During version bump, set the three hash fields to empty strings `""`.
- The user runs `scripts/deploy_version.sh` which auto-fills `hash_windows` from GitHub release and produces `hash_macos` via `build_macos.sh`.
- The agent MUST NEVER run `build_update.py` or `build_macos.sh`.

**Why it matters:** Hashes commit a real artifact's identity. Auto-filling by the agent could release a stale or wrong build.

**Related files:** `config/version.json`, `scripts/deploy_version.sh`, `scripts/build_macos.sh`.
**Related phase/commit:** Permanent.

## MEM-005 - `license.dat` choke point

**Status:** Verified
**Source:** `AGENTS.md` section 3.8 ("`license.dat` writes only via `save_license_dat()`"); `docs/RULES.md` RULE-SRC-006; `src/utils.py::save_license_dat`.

**What we know:**

- `src/utils.py::save_license_dat(data: dict)` is the **only** sanctioned writer for `license.dat`.
- It enforces UTF-8 encoding and owner-only file permissions (chmod 600).
- New code MUST go through `save_license_dat()`; never `open(get_data_path("license.dat"), "w")`.

**Why it matters:** `license.dat` is the security boundary. Scattered writes risk permission drift (audit Batch-2/D4).

**Related files:** `src/utils.py:645`.
**Related phase/commit:** Audit Batch-2.

## MEM-006 - State registry (server-driven, no desktop release needed)

**Status:** Verified
**Source:** `nrega-server/migrations/024_state_registry.sql`; `src/config.py`; `docs/PRD.md` section 2 note.

**What we know:** Adding a new state (Bihar, UP, ...) no longer requires an app release. Admin panel (`/admin/portal-states`) adds the entry; desktop app fetches `states[]` from `/api/app-config` on heartbeat (~2 min) and applies via `update_state_registry()` in `src/config.py`.

Per-state fields: `state_key`, `portal_host`, `job_card_prefix`, `demand_base_url`, `village_code_logic`, `is_active`, `sort_order`.

Built-in `STATE_PORTAL_HOSTS` / `STATE_DEMAND_CONFIG` / `STATE_JOB_CARD_PREFIXES` are **fallbacks** - registry overrides them.

**Why it matters:** Bihar was previously a release-blocker. Now it's an admin entry.

**Related files:** `nrega-server/app/routes/admin/states.py`, `src/config.py::update_state_registry`, `src/app/app_license.py::_ping_server_in_background`.
**Related phase/commit:** Server deploy migration 024 (12 Aug 2026).

## MEM-007 - Location data pool merge behavior

**Status:** Verified
**Source:** `src/location_sync.py::apply_server_data`; `tests/test_location_merge.py`; `docs/PRD.md` section 4.4.

**What we know:** When two users in the same block sync their panchayat/village data:

- Names are **UPPER-normalized** before comparison.
- Server stores `sha256(license_key)` only (DPDP - raw key never leaves client).
- Merge is **missing-only**: server data fills in panchayats/villages the local user doesn't already have.
- Local edits are NEVER overwritten by server data.
- Apply is idempotent (running twice = same state).
- Rate limits: per-key + per-IP, in `rate_limit_config.py`.

**Why it matters:** Users without PO/GP login need ready-made dropdowns. Pool sharing solves this without scraping.

**Related files:** `src/location_sync.py`, `tests/test_location_merge.py`.
**Related phase/commit:** 3.2.5+; migration 027.

## MEM-008 - Pricing DB override (no code change for price updates)

**Status:** Verified
**Source:** `nrega-server/app/services/license_service.py`; `docs/DECISIONS.md` DEC-006.

**What we know:** Plan prices and storage prices live in `app_settings` JSON (DB override). Code constants like `FIRST_TIME_PRICES` in `license_service.py` are **defaults** only.

Always read via `get_price_table(cur, table)` - never the constants directly. Otherwise admin price changes don't show up.

Tables: `first_time`, `renewal`, `storage`. Partial override is OK - missing keys fall back to defaults.

Storage order API is server-side authoritative - client `amount` is ignored (security fix).

**Why it matters:** Admin can change prices without a server deploy.

**Related files:** `nrega-server/app/services/license_service.py`, `nrega-server/app/routes/admin/pricing.py`.
**Related phase/commit:** 16 Aug 2026 deploy.

## MEM-009 - Automation lifecycle (single-sanctioned entry)

**Status:** Verified
**Source:** `src/app/app_automation.py`; `docs/NregaBot_Architecture_Audit_2026-08-29.md`.

**What we know:** `start_automation_thread()` (in `AutomationMixin`) is the **only** way to run user work. Its `wrapper()` closure's `finally:` block guarantees:

- Driver quit (if owned by this tab).
- History finish log.
- Progress clear.
- `stop_events.pop(key, None)`.
- `active_automations.discard(key)`.
- `_update_running_automation_indicator()`.
- Emergency stop button refresh.
- `restore_sleep_prevention()`.
- `on_automation_finished()` (Tk thread via `after(0, ...)`) emits toast/sound, syncs activity log + usage_stats to server.

**Why it matters:** Single entry = single place to fix cleanup bugs. Any new code path that bypasses this is a regression.

**Related files:** `src/app/app_automation.py:122-307`, `tests/test_automation_thread_lifecycle.py`, `tests/test_wrapper_tab_driver_cleanup.py`.
**Related phase/commit:** Permanent (architecture).

## MEM-010 - BrowserManager side effects (D1, D2 race conditions)

**Status:** Verified
**Source:** `docs/NregaBot_Dependency_CallGraph_Audit_2026-08-29.md` section 3.

**What we know:**

**D1 (HIGH):** Two `start_automation_thread` calls with different keys both call `get_driver()` from worker threads. For Chrome/Edge, both construct a new `WebDriver(debuggerAddress="127.0.0.1:9222", ...)`. Chrome allows only one CDP **control** client; the second connection's `execute_cdp_cmd` will fail.

Mitigation: try/except:pass in marker-keeper (marker silently fails).

**D2 (HIGH):** `get_driver()` blocks on `wait_window` modal if user has never picked. 0.2s socket timeouts make this brief; first run after launch is the realistic trigger.

**Why it matters:** These are documented races that haven't been fixed yet. New code that calls `get_driver()` from non-tab contexts may expose them.

**Related files:** `src/managers/browser_manager.py:253-279, 668`.
**Related phase/commit:** Known PLANNED.

## MEM-012 - Marker keeper behavior (per-tab daemon)

**Status:** Verified
**Source:** `src/managers/browser_manager.py`; `tests/test_marker_keeper_lifecycle.py` (500 lines).

**What we know:** When automation starts, a per-tab **marker keeper** daemon thread is spawned:

- Keeps `AUTOMATION_MARKER_JS` (bot emoji + red favicon dot) injected across navigations.
- Self-heals every 1s via `setInterval`.
- Uses a separate CDP session to re-apply the marker after navigation.
- Stops cleanly when automation finishes.

**Why it matters:** Without the marker, users might close the automation tab and not realize it's running. The marker is a UX safety feature.

**Related files:** `src/managers/browser_manager.py:_marker_keeper`, `tests/test_marker_keeper_lifecycle.py`.
**Related phase/commit:** Permanent.

## MEM-013 - Workflow polling: per-automation vs macro-global (DEFERRED)

**Status:** Verified (with caveat)
**Source:** `src/managers/workflow_manager.py:57`; `docs/PHASES.md`.

**What we know:** `_wait_for_automation_finish(key)` always checks `stop_events["macro"]` (macro-specific event), NOT the per-automation event. In practice this works for Macro Manager because the macro owns the per-automation lifecycle, but it is a latent footgun if any other caller uses `_wait_for_automation_finish`.

**Why it matters:** DO NOT MARK FIXED. See `docs/PHASES.md` Phase 2 deferred items. Future fix would add a `stop_event` parameter to allow per-key stop signals.

## MEM-014 - 11 Aug 2026 NAS Auto-Block incident (LESSON LEARNED)

**Status:** Verified
**Source:** `AGENTS.md` section 3.1 ("NAS commands and server pushes are USER-ONLY"); `docs/RULES.md` RULE-CI-002; user incident report.

**What we know:** On 11 Aug 2026, an agent's repeated SSH attempts to the NAS (`192.168.29.101`) triggered DSM Auto Block on the user's Mac IP. The deploy pipeline stalled because SSH was unreachable.

**Lesson:** The agent MUST NOT execute commands on the NAS, not via SSH, not via `ssh -t`, not via any wrapper. The agent MUST NOT push to the `nrega-server` remote. The user does all NAS work.

**Why it matters:** Encoded as `docs/RULES.md` RULE-CI-002 ("NAS commands are USER-ONLY"). Subsequent sessions obey this rule.

**Related files:** `docs/RULES.md` RULE-CI-002.
**Related phase/commit:** 11 Aug 2026 (incident); permanent rule.
